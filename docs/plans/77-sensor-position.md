# #77 — Sub-block sensor position: running order

Decision record: `docs/sensor-position.md`. This file is the delivery plan and
the record of what differed from it.

Sequencing rationale: #6 (the consumer) shipped first deliberately, so this model
is designed against a built consumer rather than a guessed one. The operator
promoted #77 ahead of #7 on 2026-08-16 because B4's adjacent-target refusal makes
#7's central move refuse in the common case on a nine-block layout.

---

## PR A — The model (`77-sensor-position-model`)

**Shipped.**

The measurement, its storage, its validated write path, its runtime state, and
the pure resolution logic. **No consumer**, so no behaviour change: every
distance the braking model computes is byte-identical to before.

- `sensors` gains `position_toward_block_id` (FK to `blocks`, `ON DELETE SET
  NULL`) and `position_offset_mm`, both nullable (D1, D3, D5).
- `domain/sensorPosition.ts` — pure: `resolveSensorPosition`,
  `positionFixFrom`, `creditedDistanceMm`, `MAX_CREDIBLE_SPEED_MM_PER_S` (D6, D7).
- `SensorObservation` gains `position` and `lastRisingEdgeAt`; `recordSensorReading`
  detects the `clear → occupied` edge; `clearSensorReading` drops the fix (D6, D11).
- `sensorCreateSchema` / `sensorUpdateSchema` / `sensorRowSchema` carry the pair;
  `LayoutService` enforces the cross-row rules (D4, D5) as a 400.
- `parseSensorRow` reads a half-set pair as unmeasured rather than throwing (D5).

## PR B — The braking consumption (`77-sensor-position-braking`)

`remainingRouteDistanceMm` gains its one optional lead term (D9); `BrakingService`
resolves the applicable fixes from `LayoutStateManager` and the live graph and
passes them down. A scenario test covering the case #77 was promoted for: a
braked run to the *immediately next* block, refused without a fix and granted
with one, plus the stale-fix and wrong-neighbour fall-throughs.

`docs/braking.md` B4's "accepted consequence" paragraph and its matching limit
are rewritten by this PR, not before it — the refusal is still real until the
term exists.

## PR C — Authoring and display

The Configure → Sensors form gains the pair, with the anchor a select over the
blocks the drawing actually connects this one to. The monitor is untouched: a
position is config, not live state, and there is no train-at-a-spot to draw
(`docs/braking.md` B7).

## Shipped, with notes

### PR A

- **The anchor is not any of the three candidates in the issue's own follow-up.**
  `(towardBlockId, offsetMm)` is a fourth, argued in D2. The short version: a
  port anchors a measurement of the railway to a picture of the railway, and an
  edge id is regenerated by every apply for the same reason a label is.
- **`MAX_CREDIBLE_SPEED_MM_PER_S` replaced the freshness window** the plan
  originally sketched (D7). One monotone constant, no cliff, self-limiting.
- The issue's decision 2 — "what is a block's length?" — was answered before this
  work started, by #105: length is on `blocks.length_mm`. Nothing here needed to
  reopen it, and D1's anchor means the length is not even required to *use* a
  position, only to sanity-check one at the write path.
