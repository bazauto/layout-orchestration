# Sub-block sensor position (#77)

> **Status: PR A shipped.** The model, its persistence, its validated write path
> and its runtime state exist; **nothing consumes a fix yet**, so the live
> layout's behaviour is byte-identical to before it landed. PR B is the braking
> consumption (D9), and it is what makes B4's adjacent-target refusal solvable.

Where a beam is, and — much more carefully — what the system is allowed to
conclude from one having been broken.

This is the semantic half of sensor location. It changes what may be concluded;
the cosmetic half (where a sensor marker is drawn) is #74's tile annotations and
decides nothing.

## The problem, in one paragraph

`docs/braking.md` B4 measures available distance as the sum of `blocks.length_mm`
over a route's **intermediate** steps. Neither endpoint contributes — not the
target block (the target is its entry boundary) and not the confirmed block,
because under block-level occupancy *a train confirmed in a block may be anywhere
within it, including hard against the exit*. A braked run to the **immediately
next** block therefore has zero available distance and is refused
(`insufficient-distance`). Westgate Hollow has nine blocks and most routes are
two or three steps, so "slow on approach to the block ahead" — #7's central move
— refuses in the common case. The fix is real position, never a fudged distance.

Everything below exists to make one sentence true and defensible: **the confirmed
block may contribute distance, but only as much as the evidence actually
supports.**

---

## D1 — A sensor's position is `(towardBlockId, offsetMm)`

A positioned sensor carries:

```
position = { towardBlockId, offsetMm }   // or null — unmeasured
```

read as: **this sensor lies `offsetMm` of track before the boundary its own
block shares with `towardBlockId`.**

Not "offset from the north end". Not "offset from the start". The measurement is
anchored to *the other block through the joint the train will cross*, which is
the only frame in which the number is directly usable: a route step running from
block *b* into block *c* wants "how much of *b* is left", and that is exactly
`offsetMm` when `towardBlockId === c`.

An operator measures it with a tape from the rail joint: *"the beam is 400 mm
back from the Goods Shed end of Platform 1."* That is the sentence a railway
modeller already says out loud.

## D2 — Why not a block-end label, a port, or a bearing

#77 as filed proposed `(blockId, endLabel, offsetMm)`, reusing the vocabulary
`block_edges` uses. **That vocabulary stopped being available** when #103 landed:
an end label is now regenerated by `compileOpenings` on every compile, unique
only *within* one compile, and referenced by nothing except the `block_edges` row
carrying it (`docs/track-graph-compilation.md` D8). Edges survive a redraw
because the apply rewrites every row in one transaction. **A stored sensor offset
would not.** Add a second opening facing the same way and `east` legitimately
becomes `east-1`/`east-2`; the stored label then names either nothing or — worse
— the wrong end of the block, which is precisely the error class that produces a
train stopped in the wrong place.

The issue's own follow-up listed three replacements. All three are rejected here:

| Candidate | Why not |
|---|---|
| **A port `(x, y, edge)`** — the boundary itself, already in `CompiledOpening.ports` | It is an anchor *on the drawing*, and a measurement of the railway must not be invalidated by an edit to a picture of it. Moving a tile does not move a beam. The candidate's stated virtue — "it does not survive the tile being moved, which is arguably correct" — is the argument the wrong way round. |
| **A reference to an edge rather than a label** | Edge ids are regenerated wholesale by every apply, for the same reason labels are. It relocates the instability rather than removing it. |
| **Store the label and diagnose drift** | Cheapest, and it fails *quiet*: a label that still exists but now denotes a different opening resolves silently to the wrong end. A diagnostic nobody reads is not a guard. |

`towardBlockId` beats all three on the property that matters: **a block id is
operator-owned, stable, and never rewritten by the compiler.** The anchor
survives every redraw, every recompile and every relabelling, and it breaks
loudly and safely in the one case where it should — the neighbouring block being
deleted or the connection being drawn away (D5).

The same argument applies to #79 (signal placement), which inherited the same
`(blockId, endLabel)` proposal and should inherit this answer.

## D3 — `null` means unmeasured, and unmeasured is exactly today's behaviour

Both columns default to NULL and nothing back-fills them. A sensor with no
position contributes no distance, which reproduces B4's worst case exactly.

This is not a new pattern: `blocks.length_mm` is nullable and NULL means
"unmeasured — unsafe for automated braking". Follow it including the refusal
posture: **the absence of a measurement is never a fault and never a
Safe-Stop**, it simply withholds a concession.

The live layout has no positioned sensors the instant after the migration runs,
so it behaves identically to the instant before. An operator opts one in.

## D4 — Only an `ir_position` sensor may carry a position

A `block_detection` sensor is a whole-block current-sensing detector: it is not
*at* anywhere. A position on one is meaningless, so the write path refuses it
with a 400 rather than storing a number nothing could honestly consume.

The check has to look at the *effective* type, not the submitted one: a partial
update that sets only a position on an existing `block_detection` sensor, and a
partial update that flips an already-positioned sensor's type *to*
`block_detection`, are both refused.

The column lives on `sensors`, not on some IR-specific table, deliberately — see
D12.

## D5 — Ambiguity and dangling anchors resolve to *unmeasured*, never to a guess

`towardBlockId` names a neighbour, and a neighbour relationship can be absent or
plural. Three cases, all resolving the same way:

1. **The anchor block was deleted.** The column is `ON DELETE SET NULL`, so the
   anchor evaporates and the position reads unmeasured.
2. **The drawing no longer connects the two blocks.** Nothing joins them, so
   `offsetMm` is a distance to a boundary that is not there. Unmeasured.
3. **The two blocks are joined at more than one place** (a loop returning on
   itself). "The boundary between *b* and *c*" is then not a definite
   description, and picking one is guessing. Unmeasured.

Resolution happens where it is consumed, against the live graph — never cached
at write time, because the drawing can change underneath a stored row and the
row is not rewritten when it does. The write path checks the same things and
reports them, but as *advice*: a 400 for a shape error (D4, a self-referential
anchor, a negative offset, an offset longer than the block), and nothing at all
for a connection that does not exist yet, because authoring order is the
operator's business and a sensor may legitimately be measured before the track
that justifies it is drawn.

**A half-set row reads as unmeasured, not as corruption.** This is the one place
`parseSensorRow`'s "a row already in the database is either valid or it is
corruption, and corruption must throw" is deliberately not applied. It is the
same argument as `grid_tiles.metadata`'s tolerant parse (`docs/track-grid.md`
D10): a fail-safe reading exists, and taking the layout down over a measurement
is worse than declining to use it.

## D6 — A trip is a fix at an instant; the fix is the *rising edge* and nothing else

A beam reading `occupied` says something is breaking it **now**. A beam reading
`clear` says nothing whatsoever (D8). Neither is a position.

The information is in the **transition**. At the moment a beam goes
`clear → occupied`, something arrived at a known spot at a known time, and on a
block held by exactly one route (D10) that something is the leading edge of that
route's train. So:

```
PositionFix = { sensorId, blockId, towardBlockId, offsetMm, at }
```

built only from a `clear → occupied` transition, recorded as
`SensorObservation.lastRisingEdgeAt`. A repeated `occupied` reading is not a new
fix — it moves `lastReadingAt` and deliberately does not move the fix, because a
device that re-publishes its state on a timer would otherwise appear to re-observe
a train that has long since gone.

**"Leading edge", not "front".** A propelled move puts a wagon first; the fix is
about whatever end of the train is furthest along in the direction of travel,
which is the end that matters for a collision.

A subsequent `clear` does **not** invalidate the fix. The whole train having
passed the beam only means more time has elapsed, which D7 already accounts for.

## D7 — A fix decays by a worst-case travel allowance, not by a freshness cliff

A fix taken at `at` is worth less at `now`, because the train has been moving. The
system has no odometer and no speed calibration, so the honest treatment is a
**bound**, not an estimate:

```
allowanceMm  = MAX_CREDIBLE_SPEED_MM_PER_S * (now - at)
creditedMm   = max(0, offsetMm - allowanceMm)
```

The train cannot have travelled further than a deliberately generous layout-wide
maximum speed permits, so subtracting that allowance can only ever *understate*
the distance remaining — the safe direction. An old fix decays to zero
contribution on its own, which is why there is no separate expiry constant and no
cliff to tune.

Rejected alternatives:

- **Dead reckoning from commanded speed.** `brakingFactor` predicts a stopping
  *distance*; nothing in this system maps a DCC speed step to mm/s. Estimating
  position from it would be guessing a train's position, which safety rule 1
  forbids outright.
- **A fixed freshness window.** Same unmeasured constant, plus a discontinuity:
  a fix is fully trusted at 999 ms and worthless at 1001 ms. The allowance is
  monotone and self-limiting.

`MAX_CREDIBLE_SPEED_MM_PER_S = 500` — about 85 scale mph at 1:76.2, comfortably
above anything Westgate Hollow runs. It is exported and named for the same reason
`REFERENCE_STOPPING_DISTANCE_MM` is: being wrong *high* is fail-safe, so it is
set high and left alone.

## D8 — Knowing where a beam is does NOT let an IR `clear` clear a block

**`deriveBlockOccupancy` clause 3 is untouched by this issue and must stay
untouched.** An IR sensor may raise occupancy and may never lower it. A beam
being unbroken is not evidence the block is empty, *no matter how precisely the
beam's position is known* — a train standing beyond the beam breaks nothing, and
a train that has passed the beam entirely leaves it clear.

This is stated here, in the decision record, and not only in a comment above
clause 3, because the tempting simplification arrives with exactly this feature:
"we know where the beam is now, so surely a clear beam tells us something." It
does not. Any change that makes an IR `clear` contribute to a block being
`clear` has reintroduced the failure `domain/occupancy.ts` exists to prevent.

What position adds is strictly a *positive* statement — "the leading edge was at
least this far along at time T" — used only to credit distance the system was
previously unwilling to promise.

## D9 — A fix credits the confirmed block only, toward the next step only

`remainingRouteDistanceMm` gains one optional term and no new behaviour anywhere
else. The credited distance is added only when every one of these holds:

- the fix's block **is** the route's confirmed block, `path[confirmedIndex]`;
- the fix's `towardBlockId` **is** the next step's block,
  `path[confirmedIndex + 1]` — so the beam is measured toward the boundary the
  train is actually about to cross, not some other exit from a branching block;
- the sensor is contributing (in service, unfaulted) by exactly the rule
  `isContributingSensor` already applies to occupancy;
- `creditedMm > 0` after D7's allowance.

Intermediate and target blocks contribute nothing extra — their whole length is
already counted, or deliberately not counted, by B4.

**Several applicable fixes take the minimum**, not the newest. A minimum needs no
argument about which observation supersedes which, and it is the fail-safe pick
in every ordering.

**An absent, stale or inapplicable fix is never a refusal.** It falls through to
the B4 sum unchanged. The whole feature can only ever hand back distance the old
model refused to promise; it can never take distance away, and it can never turn
a run that would have been granted into one that is not.

## D10 — Whose train broke the beam

The fix assumes the train that broke the beam is the one the route belongs to.
That is not a new assumption: `ReservationService.onOccupancyChange` already
treats occupancy appearing in a route's held block as that route's train, and
holds the block exclusively so nothing else may be routed onto it. The fix is
consumed only against a route holding the block in question, so it inherits that
guarantee rather than adding one.

Where it would be wrong — a shunter placed on the track by hand, a wagon rolling
away — the system is already wrong in the same way, and already responds through
`unexpected-occupancy` and the overrun check (B5).

Identity of the vehicle is #39's problem, not this one's.

## D11 — Nothing about a fix is persisted

`lastRisingEdgeAt` is runtime state on `SensorObservation`, rebuilt from scratch
on every start, exactly like `lastReading` and everything in `PointState`
(`docs/point-feedback.md` D2). Only the *measurement* — the operator's tape
reading — is a database row.

A persisted fix is a retained message with better durability: a position observed
before a restart says nothing about where the train is after one, and a stack of
them would let the system resume with a confident, wrong belief about a train it
has not seen since. A sensor going out of service or faulting clears the fix with
the reading, for the same reason (DD6).

## D12 — Position is a property of a sensor, not of an IR sensor

`#39`'s RFID reader is also a point observation at a location, and would want
this model verbatim. So the columns live on `sensors`, the type is
`SensorType`-agnostic, and D4's restriction is a *validation rule about which
types may carry one today* — not a shape baked into the schema. Adding
`rfid_reader` to `SensorType` later needs one line in that rule and nothing else.

## What this deliberately does not do

- **Continuous position tracking.** There is no "where is the train now" value
  anywhere. A fix is an observation at an instant with a decay bound, consumed
  where it is needed and never accumulated into a running estimate.
- **Change occupancy derivation** (D8).
- **Give the pathfinder anything.** Distance-to-a-beam is not a search cost;
  `docs/pathfinding.md` P2's `DEFAULT_BLOCK_LENGTH_MM` posture is untouched.
- **Berth a train inside a block.** "Stop at the beam" is the natural next
  consumer and needs an anchor measured from the *entry* side; the model extends
  to it (a second `(towardBlockId, offsetMm)` pair, anchored the other way) but
  nothing here builds it.
- **Change the MQTT contract.** A sensor's reading payload is unchanged; the
  position is config, held entirely backend-side.
- **Decide when to brake.** That is #7, and it is still the whole #6/#7 boundary.

## Limits recorded rather than closed

- **The measurement is unverifiable authored data**, like a point tile's leg
  mapping (`docs/track-grid.md` D9). Nothing can check with a tape measure. The
  write path checks only what is checkable: the anchor is a different block, the
  offset is positive, and it does not exceed the block's own measured length.
- **A beam measured toward one neighbour helps only in that direction.** A block
  with the beam authored toward *c* gets no credit on a route leaving toward *d*,
  and none at all in the reverse direction. This is deliberate under D1: the
  alternative — deriving the far side as `length_mm - offsetMm` — is exact only
  for a block with exactly two openings, silently wrong for a branching one, and
  wrong in the *overestimating* direction, which is a collision. A second
  measurement is a second row's worth of honest data, not a derivation.
- **`MAX_CREDIBLE_SPEED_MM_PER_S` is a guess**, like
  `REFERENCE_STOPPING_DISTANCE_MM`. It is set high on purpose; the correct
  response to it being wrong is to leave it alone unless it is wrong *low*.
- **A fix cannot be confirmed.** Everything B7 says about open-loop dead
  reckoning applies: this narrows the uncertainty, it does not close it.
- **Nothing authors a position in the UI yet.** PR C. Until then the columns are
  reachable through `PUT /api/layouts/:layoutId/sensors/:id` only.
